# Architecture notes

Internal notes on how `plugin.py` is put together, for future maintenance. See `README.md` for user-facing documentation.

## Polling model

Indigo's `runConcurrentThread` runs a plain synchronous loop, ticking every 5 seconds. Each enabled `inverter` device is polled independently once its own configured `pollInterval` has elapsed (tracked in `self._next_poll_at`), so multiple inverters can be polled at different rates without blocking each other — a failure on one device (caught individually, logged via `logger.exception`) never stops the loop or affects other devices.

## Device model: one connection, four devices

The plugin models the physical inverter as a parent `inverter` device plus three auto-discovered children (`solarDevice`/`batteryDevice`/`gridDevice`), each holding a `systemDevice` prop pointing back at the parent's device ID (same parent/child pattern [MyAir](https://github.com/coolcaper777/myair) uses for its zone devices). This exists because the natural grouping of AlphaESS telemetry (solar/battery/grid) maps better onto separate Indigo devices than one monolithic device — cleaner trigger/Control Page picking, and each domain can independently show its own error state rather than one shared "something's wrong" indicator.

Since AlphaESS inverters accept only **one** Modbus TCP connection at a time (see below), all four devices are updated from a *single* poll/connection per cycle — `_poll_inverter` (still keyed off the parent `inverter` device in `runConcurrentThread`/`self._next_poll_at`) does the one Modbus session and fans the results out to whichever children exist, rather than each device polling independently.

`_get_or_create_child`/`_find_child` look children up by `systemDevice == str(parent_dev.id)`; the former creates one if missing (deferred, like MyAir's zone discovery, while the parent still has Indigo's placeholder name - `NEW_DEVICE_NAME_RE`). `_set_children_error` sets an error state on whichever children already exist, without creating new ones, for failures that happen before any register read is even attempted (bad config, connect failure).

## Register reads (`_poll_inverter`)

Each poll opens a fresh `ModbusTcpClient` connection and does 4 batched `read_holding_registers` calls (`REGISTER_CLUSTERS`) - grid: 16-34, solar+inverter-health/work-mode/grid-frequency: 1052-1088, battery: 256-295, inverter clock: 1856-1858 - closing the connection in a `finally` block. Batching exists purely to keep each poll to 4 round trips instead of 40+; every address in `REGISTERS` falls inside one of the four cluster ranges (confirmed programmatically - see the register-coverage check run when this was last extended). The inverter clock lives far from every other cluster, so it's its own extra round trip rather than folded into an existing one.

`_decode_value` combines 1 or 2 raw 16-bit registers into a signed/scaled float — `words: 2` means high-word-first, two's-complement if `signed`. `pvPower` is *not* read from the single "PV meter" register (161) — that's an optional external CT accessory that reads flat 0 without one wired up. It's computed instead by summing the six individual `pv{n}Power` values (each itself read directly off an MPPT tracker, same as the per-string voltage/current now also exposed alongside it).

**Register map cross-checked against `senalse/ha-alphaess-modbus`, a more actively-documented AlphaESS Modbus project (independent from `SorX14/alphaess_modbus`, the plugin's original register source) whose `docs/register_map.md` and Hillview Lodge's published Home Assistant YAML (`projects.hillviewlodge.ie/alphaess`) the user confirmed is verified working against their own hardware.** This surfaced two real bugs beyond the original frequency-scale fix:

- `gridFrequency` is read from address **1052** (`0x041C`), not address 26 (`0x001A`, `SorX14`'s "frequency_grid") - Hillview's verified `AlphaESS_Inverter_Grid_Frequency` sensor reads 1052 exclusively and never references register 26 at all. `decimals: 2` was already right once fixed; the address itself was the deeper issue, so this reads a properly-documented register instead of just patching the scale on a dubious one. 1052 sits one register before the solar cluster's old start (1053), so `SOLAR_CLUSTER_START` was moved back by one to cover it for free. Because it now lives in a different cluster than the rest of the Grid device's data, `_poll_inverter` writes it in its own `if solar_ok:` block, independent of `grid_ok`.
- `gridVoltage`/`gridVoltageB`/`gridVoltageC` use `decimals: 0` (scale ×1), not `decimals: 1` (×0.1) - per `senalse/ha-alphaess-modbus`, ×0.1 only applies to the SMILE-B3/SMILE-B3-PLUS model variant; every other model uses the raw register value directly as volts. Inferred the user isn't on that variant because `invTemperature` carries the identical model-specific exception (×0.01 instead of ×0.1) and has never shown an implausible reading.

Grid current (addresses 23-25, same cluster, same naming convention as voltage/power) is deliberately **not read at all** - neither Hillview's config nor `senalse/ha-alphaess-modbus` exposes it, despite both being thorough about everything else in this same register block. User's call once that gap was flagged: don't guess at a value neither verified source confirms, rather than ship an unconfirmed reading the way `gridFrequency` briefly was. It's derivable from `gridPower / gridVoltage` per phase if ever needed - exactly for a purely resistive load, only approximately otherwise since `P = V × I × cos(φ)`.

`_decode_system_time` decodes the 3-register inverter clock (year/month, day/hour, minute/second, each register packing two plain byte values, high byte first) - cross-checked against **two** independent sources that both decode it the same way: `SorX14/alphaess_modbus`'s `formatter.py` and `senalse/ha-alphaess-modbus`'s `AlphaESS_System_Date`/`AlphaESS_System_Time` Jinja templates (verified working on the user's own hardware).

`invWorkMode`'s numeric codes are only documented for `1` (Normal) and `2` (Bypass/EPS) - both Hillview's register docs and `senalse/ha-alphaess-modbus` describe anything else as "model-specific." (Hillview's own `AlphaESS_Current_House_Load` template treats work mode `2` as a distinct case - house load becomes just grid power rather than the usual PV+battery+grid sum - consistent with `2` being an off-grid/bypass state where the normal power balance doesn't hold.) Anything outside those two codes is shown as `Unknown work mode (N)` rather than guessed.

`batteryFull` is decoded from the BMS's own `battery_status` register (address 259, inside the battery cluster) as `battery_status == 1` - per `senalse/ha-alphaess-modbus`'s own `AlphaESS_Battery_Full` template, confirmed working against the user's real hardware. An earlier version of this feature computed `batteryFull` from `batterySoC >= 99.5` instead, because at the time no source documented `battery_status`'s enum values at all - replaced once a verified decode turned up. No codes other than `1` are documented, so nothing else is inferred from this register.

## Error states: per-cluster isolation

Each of the 4 register clusters is read (and its `ModbusException`, if any, caught) **independently** inside `_poll_inverter`'s loop, tracked in `cluster_registers`/`cluster_errors` keyed by cluster start address. This matters specifically because of the device split above: a failure reading the battery cluster (e.g. a battery-less installation refusing that address range - still unverified, see `README.md`) sets an error state on just the Battery device, while Solar and Grid update normally from their own successful reads. The parent Inverter device's `loadPower` is only computed (and only written) when the grid/solar/battery clusters all succeed in the same cycle - skipped rather than computed from a partial/stale mix otherwise, with `dev.setErrorStateOnServer(...)` naming which domain(s) were missing that cycle. `invTemperature`/`invWorkMode` and the Grid device's `gridFrequency` all depend on the solar cluster (not the grid cluster, despite `gridFrequency`'s name - see the register-map note above), and `systemTime` depends on its own small clock cluster, so all of these update independently of `loadPower`'s three-way requirement (and don't factor into the "Partial read" error message at all - a clock-read hiccup shouldn't flag the whole device red).

A genuinely unmodeled exception (decode bug, etc.) still aborts the whole poll and sets an error state on the parent plus every already-existing child (`_set_children_error`) - only the two *expected* failure modes (per-cluster Modbus errors, and total connect failure) get the more granular treatment.

## Dispatch writes (`force_charging_action` / `force_discharging_action` / `force_import_action` / `dispatch_action` / `dispatch_reset_action`)

Actions, not a new device type — each dispatch command is a one-shot parameterized write (Indigo's Action model), not persistent state, and scoping them to `deviceFilter="self.inverter"` in `Actions.xml` avoids having to hand-roll mutual exclusivity across separate devices the way the reference HA integration's stateful switch entities need to (`_MUTEX_SWITCHES`/`_async_turn_off_silent()` in `senalse/ha-alphaess-modbus`'s `switch.py`). The inverter only ever holds one Dispatch configuration on the wire regardless of how many Indigo Actions exist, so `_start_dispatch` doesn't need to "turn off" anything before writing — a new dispatch simply supersedes whatever was active, and the tracked state (`dispatchActive`/`dispatchType`/etc.) is just overwritten to match.

All four writes go through `_write_dispatch`, one atomic `client.write_registers(DISPATCH_START_ADDRESS, [...], device_id=unit_id)` call against the 11-register block at `0x0880`-`0x088A` (function code 16) - confirmed **not** flash-backed (see the `DISPATCH_START_ADDRESS` module comment for the source), unlike the inverter's scheduler-config registers (max feed-to-grid, charge/discharge cutoff SoC/time periods), which this plugin never writes at all. `_open_dispatch_client` mirrors `_poll_inverter`'s connect logic but deliberately does *not* set the device's Indigo error state on failure - a dispatch write failing shouldn't overwrite whatever error/OK state the last register *poll* left in place, since those are reported independently.

Force Charging/Force Discharging always write Dispatch Mode 2 (`DISPATCH_MODE_SOC_CONTROL`) - matching `switch.py`'s reference implementation, which does the same for every one of its "Force" convenience switches and never exposes a mode picker on them. This isn't a simplification: mode 2 is the only mode where both the power word *and* the SoC-target word are honored by the inverter in the sense this plugin's fields assume (modes 1/3/5 honor power as a rate but ignore the SoC word) - exposing mode choice on these two actions would let a user pick a combination where their power/cutoff-SoC fields silently do nothing or, worse, do something unexpected. `dispatch_action` (the generic action) is the only one with a mode picker, and its `if mode in (1, 2, 3, 5): ... else: power_raw = 32000` / `soc_raw = ... if mode == DISPATCH_MODE_SOC_CONTROL else 0` branches encode the applicability rule for modes 1/2/3/5 specifically.

**Correction (2026-09-01):** this section previously claimed modes 4/6/7 (plus 19) "ignore power entirely and run neutral," sourced only from `senalse/ha-alphaess-modbus`'s `register_map.md`, which that project's own earlier read of this plugin's history flagged as having "no further per-mode description... only bare option names." Live-tested against the real inverter and cross-checked against Hillview Lodge's own detailed writeup (`https://projects.hillviewlodge.ie/alphaess/#dispatch`), which neither this plugin nor that assumption had been checked against before: **modes 4/6/7 are not neutral at all.** Mode 4 ("Maximise Output") actively discharges the battery to maximise grid feed-in. Mode 6 ("Optimise Consumption") force-charges the battery from the grid at full power. Mode 7 ("Maximise Consumption") does the same as 6 but also disables PV output. All three ran at several kW in the live test regardless of this plugin's Power/Cutoff SoC fields being left at whatever they were last set to, which were never varied in that test - so it remains untested (not confirmed either way) whether they *also* respond to the Power word as a rate, or run a fixed internal algorithm regardless of it. Either way, "neutral" was wrong, and `dispatch_action`'s mode picker exposes these three today without any warning to that effect - worth a UI-level caution at some point, not yet added.

`_resolve_number` implements the two-tier config model: an Action instance's own field (blank if left empty) is tried first, then the Force action's configured default on the Inverter device's `pluginProps` (`forceChargingPower`/etc., added to `Devices.xml`), then a hardcoded fallback if both are blank/invalid. This is what makes a zero-parameter "Force Charging" action usable from a Control Page button or a HomeKit-bridge-style trigger, while still letting a specific Action Group step override the power for a time-of-use window.

**Parameter validation** (`_validate_dispatch_number`) runs on every resolved value before `_start_dispatch` is ever called - `DISPATCH_SOC_MIN`/`MAX` (4-100%), `DISPATCH_DURATION_MIN`/`MAX_MINUTES` (0-480), and `DISPATCH_POWER_ABSOLUTE_MAX_KW` (20, further capped per-device by `_resolve_power_limit_kw`'s `acLimitKw` prop). These ranges were cross-checked against two independently maintained reference sources that agree exactly: `senalse/ha-alphaess-modbus`'s `NUMBER_REGISTERS` (`custom_components/alphaess_modbus/const.py` - the min/max declared on its HA number-entity sliders for these same fields, including the `ac_limit_scaled` behavior mirrored by `acLimitKw`) and Hillview Lodge's `integration_alpha_ess.yaml` `input_number` helpers. A value outside range logs an error and aborts the action before any Modbus write - matches this plugin's established "reject clearly-bad input rather than send it to the hardware" posture (`validateDeviceConfigUi`, the Port/Unit ID `int()` guards). `dispatch_action`'s Power/Cutoff SoC checks are conditional on the selected mode, matching the same mode-applicability rule already encoded in which register words actually get a non-neutral value (see the mode discussion above) - validating a field the inverter will ignore anyway would reject harmless leftover input.

Auto-off (`_dispatch_end_at`, a `dev.id -> epoch time` dict) is checked on `runConcurrentThread`'s existing 5-second tick, independent of each device's own (possibly slower) `pollInterval` - the same loop iteration that polls registers also checks whether any tracked dispatch has passed its end time and calls `_stop_dispatch(dev, reason="duration expired")` if so. This mirrors the reference implementation's in-memory `_schedule_auto_off` timer without needing any Indigo-side scheduling. `deviceStopComm` clears `_dispatch_end_at` for a disabled/deleted device, same as it already does for `_next_poll_at`.

**Dispatch state readback (`_poll_inverter`, `dispatchModeRaw`/`dispatchActivePowerRaw`/`dispatchSocRaw` in `REGISTERS`), added 2026-09-01.** Until this point, `dispatchActive`/`dispatchType`/`dispatchModeLabel`/`dispatchPowerTarget` were purely write-side bookkeeping - set only by `_start_dispatch`/`_stop_dispatch`/the Force Import servo, never checked against what the inverter is actually doing. Found to be a real gap while live-testing against the same inverter through Home Assistant's Hillview integration in parallel (still running - the two systems aren't cut over yet): HA's own dispatch UI (its `input_select`/`input_number` helpers) turned out to be exactly this same kind of write-only state, and went stale/wrong the moment this plugin wrote to the inverter independently of HA - HA had no way to know. This plugin had the identical latent bug, just not yet caught in practice since nothing else was writing to the inverter through it before now.

Fixed by adding the 11-register dispatch block (`DISPATCH_START_ADDRESS`, 2176-2186) as a 5th `REGISTER_CLUSTERS` entry, decoding word 5 (mode), words 1-2 (active power, still 32000-biased on the way back out - `raw - 32000` recovers the same signed-watts convention `dispatchPowerTarget` already used), and word 6 (SoC target, `* DISPATCH_SOC_SCALE`) the same way every other register is decoded. `_poll_inverter` now overwrites `dispatchActive`/`dispatchModeLabel`/`dispatchPowerTarget`/the new `dispatchCutoffSoC` state from this readback every poll cycle, treating mode `0` as "nothing active" (matches every observed "no dispatch engaged" reading against this hardware, cross-checked against HA's own `sensor.alphaess_dispatch_mode` throughout this week's testing). `_start_dispatch`/`_stop_dispatch` still write their optimistic values immediately for instant UI feedback - the next poll's readback either confirms or corrects them, so a momentarily-optimistic value between an action firing and the next poll is harmless.

`dispatchType` (which Indigo action started a dispatch) and `dispatchEndsAt` (when this plugin expects to stop it) have no register equivalent - the inverter doesn't track "who" dispatched it or expose a remaining-time countdown (the Time word reads back as the *configured* duration, confirmed unchanged across several minutes of live observation, not a live countdown). Those two stay write-side/informational and are only cleared (not otherwise corrected) when the readback confirms nothing is active - if something external re-engages dispatch, `dispatchModeLabel`/`dispatchPowerTarget`/`dispatchCutoffSoC` will correctly reflect it, but `dispatchType` may still show whichever Indigo action last ran, since there's no way to attribute an external change to "who" caused it.

## System health (`systemHealthOK`/`systemHealthDetail`), added 2026-09-01

Prompted by the user noticing HA's "Warnings and Faults" section and asking whether it's worth porting. Checked what's actually there before proposing anything: AlphaESS exposes `system_fault` (0x08D4), `inverter_warning_1`/`_2` + `inverter_fault_1`/`_2` (one bitmap each, split across 2 uint32 words - 1078/1080/1082/1084), `battery_warning`/`battery_fault` (aggregate across modules, 284/286), plus 12 more per-module `battery_N_warning`/`battery_N_fault` registers (0x0131-0x0147) that `senalse/ha-alphaess-modbus` itself ships disabled by default. None of the 7 default-enabled bitmaps has a documented per-bit meaning anywhere checked - not Hillview Lodge's page, not `senalse/ha-alphaess-modbus`'s `register_map.md`/`const.py`, not HA's own entity attributes for these same registers (confirmed by reading them directly via the API). Even the "official reference" implementations only treat these as "zero = healthy, non-zero = something's wrong."

Given that, exposing all 7 (or all 19, including the per-module ones) as permanent Indigo device states would just be clutter for values that read `0` essentially forever - the same instinct that led the user to ask the question in the first place. Condensed instead into `systemHealthOK` (Boolean) and `systemHealthDetail` (String, blank when healthy) - computed in `_poll_inverter` from the 6 free reads (already inside `SOLAR_CLUSTER_START`/`BATTERY_CLUSTER_START`'s existing ranges, no extra Modbus round trip) plus `system_fault`, which needed one new 2-word cluster (`SYSTEM_FAULT_CLUSTER_START = 2260`, following the same load-order-before-`REGISTERS` pattern `DISPATCH_START_ADDRESS` already established, for the same reason - caught this exact class of bug again while writing this, see the git history/memory for how it was caught before committing this time). The 12 per-module registers are deliberately not read at all - the aggregate `batteryWarningRaw`/`batteryFaultRaw` already cover "something's wrong with a module," matching upstream's own disabled-by-default choice for the granular ones. The dashboard's header meta line shows a warning glyph + `systemHealthDetail` only when unhealthy, nothing extra when everything's fine - consistent with the "condense, don't clutter" ask.

**Upgraded same session to decode actual bit names, not just raw numbers.** The "no documented per-bit meaning anywhere" claim above turned out to be about community sources specifically - AlphaESS's own official "Household Modbus Register Parameter List" PDF (66 pages, not linked directly from AlphaESS's own site but mirrored at `https://projects.hillviewlodge.ie/_alphaess/` - fetching it needs a `Referer` header set to that site or the host 403s a direct request; `pdftoppm`/poppler wasn't installed locally so `pypdf` was used instead to extract text) has full bit-level fault/warning tables (Note4/Note6/Note26/Note28/Note32). `SYSTEM_FAULT_BITS`/`BATTERY_FAULT_BITS`/`BATTERY_WARNING_BITS`/`INVERTER_FAULT1_BITS`/`INVERTER_FAULT2_BITS`/`INVERTER_WARNING1_BITS`/`INVERTER_WARNING2_BITS` (near `_decode_fault_bits`, just above `_decode_value`) hold these, transcribed from the PDF's text extraction. Two of the seven (`SYSTEM_FAULT_BITS`/`BATTERY_FAULT_BITS`) are flagged in their own comment as best-effort: their source table has two columns for different EMS firmware platforms that couldn't be reliably attributed per-bit from the flattened PDF text, so where the two names differed both are joined with `" / "` rather than guessing which applies to this specific inverter. The other four (inverter fault/warning 1 vs 2) are exact - their two columns are genuinely two separate registers, not a platform split. `systemHealthDetail` now reads e.g. `Battery Fault: Charge Over Current / Slave battery communication lost` instead of `Battery Fault=4`.

**Also found while reading that same PDF, not yet acted on:** the official Dispatch Mode table (Note29) confirms modes 1-7/19 exactly as already implemented, and reveals three more modes this plugin's picker doesn't expose - 8 (ECO Mode), 9 (FCAS Mode), 10 (PV Power Setting) - plus, separately, mode 20 ("BurnIn Mode"), which takes Charging/Discharge cutoff SoC as parameters and looks like it could be AlphaESS's actual dedicated calibration mode, rather than this plugin's current approach of just waiting for SoC to naturally reach 100% and resetting a counter. Flagged for future investigation, deliberately not pursued this session.

## Force Import servo loop (`force_import_action` / `_service_force_import`)

Unlike the three fire-and-forget writes above, Force Import can't be satisfied with a single register write: the dispatch block only accepts a fixed *charge power* word, but the actual goal is a fixed *grid import* level, and house load/PV shift continuously. Ported directly from `senalse/ha-alphaess-modbus`'s `switch.py` (`_compute_force_import_power_raw`/`_start_force_import_watcher`, read in full before implementing, not guessed at) - deferred at the same time as Force Export/Excess Export when Dispatch v1 shipped, since all three need this same class of standing control loop; Force Import was the one actually needed (see [[ha_to_indigo_alphaess_automations]] in project memory for why - it's the mechanism behind the user's Home Assistant top-up cascade), so it's the one built first.

`force_import_action` writes an initial **feed-forward seed**: `charge_w = max(0, target_import_w - load_power + pv_power)`, using this same poll cycle's already-cached `loadPower`/`pvPower` states (no extra Modbus round trip) - accurate at the moment of turn-on, before the battery has started actually dispatching. `_service_force_import`, called once per poll from the end of `_poll_inverter` for any inverter with an entry in `self._force_import_state`, then takes over with two independent checks per cycle, in this order:

1. **Early stop** - if `batteryPower` has stayed within `FORCE_IMPORT_NEAR_ZERO_BAND_W` (50W) of zero for `FORCE_IMPORT_NEAR_ZERO_HOLD_S` (10s), the inverter's own SoC Control loop has already reached the cutoff and settled to near-zero net battery flow - calls `_stop_dispatch` immediately rather than waiting out the full configured duration. This is the same signal `switch.py`'s `_start_battery_power_watcher` uses (there, on a 2s cadence; here, once per poll) - it's an indirect but reliable way to detect "target SoC reached" without separately polling/comparing live SoC against the cutoff in software, since the inverter's own firmware is what's actually enforcing that comparison.
2. **Grid-error servo** - trims the charge word so measured grid power converges on the import target: `new_charge = current_charge + FORCE_IMPORT_SERVO_GAIN * (target - measured_grid)`, clamped to `[0, power_limit_w]`. Deliberately closes the loop on the grid meter alone, never on the calculated house-load estimate - `switch.py`'s own comment explains why: house load is itself derived from `pv + battery + grid`, so feeding it back drove a kilowatt-scale limit cycle (the battery's own output feeding into its next command). A rewrite is only issued once the setpoint moves by `FORCE_IMPORT_SERVO_DEADBAND_W` (80W) or `FORCE_IMPORT_STALE_REWRITE_S` (60s) has elapsed since the last write - avoids a Modbus write every single poll for a setpoint that's already converged.

**Deliberate cadence difference from the reference implementation.** HA services this loop on every coordinator update (~2s). This plugin services it once per poll cycle instead (`pollInterval`, default 30s, same tick that already reads fresh grid/battery values - no separate fast timer). Flagged explicitly, not an oversight: the gain/deadband/staleness constants are copied verbatim from a loop tuned for 2s responsiveness, so convergence here is proportionally slower - acceptable for a multi-hour grid-top-up goal, not verified acceptable for a tighter use case (e.g. a zero-export tariff) that `switch.py`'s own comment says the tuning was specifically chosen for. Revisit the gain/cadence together if this is ever repurposed for something latency-sensitive.

`_start_dispatch` now returns `bool` (previously `None`) so `force_import_action` can avoid populating `self._force_import_state` for a dispatch that never actually got written (a connection/Modbus failure) - the three existing callers (`force_charging_action`/`force_discharging_action`/`dispatch_action`) still ignore the return value, unaffected. `_stop_dispatch` pops `self._force_import_state` unconditionally, so every stop path - explicit Dispatch Reset, the 5-second-tick duration auto-off, or the servo's own early-stop - correctly tears down the tracking without three separate cleanup call sites.

## Force Import Pause/Resume safety mechanism (`_track_sustained` / `_service_force_import`)

Ported from Hillview Lodge's `integration_alpha_ess.yaml` (`AlphaESS_Force_Import_Pause`/`_Resume`, read in full before implementing) - a real gap `senalse/ha-alphaess-modbus`'s `switch.py` doesn't address at all. Added after the user reported the discussion prompted by asking why Force Import was built from senalse's source rather than Hillview's, the integration they'd actually been running.

**Pauses** (writes a neutral dispatch - `[0, 0, 32000, 0, 32000, 0, 0, 0, 90, 255, 0]`, matching Hillview's exact register values including its own `90`-second duration word, preserved as observed rather than guessed at since it's unclear whether that value is even interpreted once the Start word is `0` - but keeps the session tracked as *paused*, not stopped, so the overall duration/auto-off keeps counting down regardless, matching the source) when any of: the target can't actually be met without draining the battery (`load − PV > target_import`, the only one of the three pause conditions with a sustain requirement in the source), PV production is clipping against the AC limit, or the inverter has left Normal work mode at all (covers a grid-outage Bypass/EPS event - Hillview's own condition reads like it came from a real incident). **Resumes** only once work mode has been confirmed Normal for a full 10 minutes (`FORCE_IMPORT_RESUME_NORMAL_HOLD_S`) AND the overload/clipping conditions have cleared - deliberately conservative, not a quick bounce-back, matching the source exactly.

**`_track_sustained`** is a small addition beyond a straight port, prompted by the user asking a sharp question mid-design: Hillview's HOLD_S-style thresholds (5s before pausing, 10 minutes before resuming) are wall-clock durations, evaluated on HA's near-continuous event-driven triggers - but this plugin only samples once per poll, and `pollInterval` is user-configurable (10-300s). A pure elapsed-time check breaks down for a slow poller: with a 300s interval and a 10s threshold, the *very first* observation already satisfies "10 seconds have passed" by the time a second poll arrives, without anything having actually been confirmed sustained - just two samples 300s apart that both happened to qualify. `_track_sustained` additionally requires `FORCE_IMPORT_MIN_SUSTAINED_POLLS` (2) consecutive qualifying polls regardless of elapsed time, so a single instantaneous reading can never satisfy a "sustained" check no matter how slow or fast a given user's `pollInterval` is - the most honest guarantee obtainable given the actual sampling rate, rather than a threshold whose real meaning silently depends on a poll rate nobody chose with that number in mind. Used by all three HOLD_S checks (overload-before-pause, normal-before-resume, and retrofitted onto the pre-existing near-zero-battery early-stop check, which had the exact same latent bug). The two *other* Hillview pause/resume sub-conditions (PV clipping, work-mode-not-Normal on the pause side; overload-cleared, not-clipping on the resume side) have no `for:` clause in the source and are checked instantaneously each poll, matching that asymmetry exactly rather than uniformly applying a sustain requirement everywhere.

**Interaction with the pre-existing near-zero-battery early-stop**: pausing deliberately zeroes the dispatch, which would otherwise trivially satisfy "battery settled near zero" and cause the early-stop to misfire as if the SoC target had been reached. Guarded two ways: the early-stop check only runs in the non-paused code path at all, and both entering and leaving a pause explicitly reset `near_zero_since`/`near_zero_count`, so neither a paused period's artificially-zero readings nor stale pre-pause tracking can leak into the check once normal servicing resumes.

**Bookkeeping consistency on pause**: the pause write also updates `state["last_power_raw"]` to `32000` (neutral) and `state["last_write_time"]`, matching what's now actually on the wire - without this, the servo's next correction after resuming would compute its starting point from stale pre-pause data instead of the neutral state the inverter was actually left in during the pause.

Verified via a standalone Python simulation (not just `ast.parse`) of `_track_sustained` against a fast-poller scenario (10s poll/10s hold - satisfied from the 2nd poll, as intended), the slow-poller scenario that motivated the fix (300s poll/10s hold - a single poll can never claim sustained, satisfied on genuine 2nd observation), and a flicker scenario (condition drops false partway through - resets fully rather than pausing the counter); and a second simulation of the full pause-trigger/resume-gate decision tree across representative scenarios (Bypass/EPS, unrecognized work-mode code, PV clipping, sustained vs. not-yet-sustained overload, and all three resume-gate combinations). All passed. **Not yet live-tested against the real inverter or a real Bypass/EPS event** - this session has no hardware access.

Force Export, Excess Export. Both need the same class of continuous servo loop as Force Import, on the export side of the meter instead (`switch.py`'s `_start_force_export_watcher`) - deferred to a future release.

## Single-connection limitation

AlphaESS inverters accept exactly one Modbus TCP connection at a time — a second concurrent connection gets an immediate refused connection, not a timeout. This isn't handled specially in code; it just surfaces as an ordinary "Connection failed" error state if something else (Home Assistant, etc.) is already connected. See `README.md`'s troubleshooting section for the TCP-proxy workaround.

## HTTP dashboard (`dashboard` / `dashboard_data`)

Reachable at `http://<host>:8176/message/com.coolcaper.alphaessmodbus/<id>` via Indigo's built-in plugin HTTP responder — registered in `Actions.xml` as `<Action id="..." uiPath="hidden"><CallbackMethod>...</CallbackMethod></Action>`, per Indigo's official `Example HTTP Responder` SDK sample. **Both callback signatures must stay untyped** (`def dashboard(self, action, dev=None, caller_waiting_for_result=None):`, no type hints or return annotation) — Indigo's HTTP-dispatch bridge fails on this specific path with an opaque `RuntimeError: unable to convert python exception`, raised *before* the method body ever runs, if the signature carries type hints. Both methods also wrap their own bodies in `try/except Exception` and log via `self.logger.exception` before returning a `500` — Indigo's own exception-marshalling for this dispatch path can itself fail silently, so this is the only reliable way to see what actually went wrong.

`dashboard` returns the static `DASHBOARD_HTML` page (inline CSS/JS, no CDN dependency, dark-mode aware via `prefers-color-scheme`). `dashboard_data` returns current state as JSON for the page's 5-second client-side poll; if more than one inverter device exists, it supports a `?deviceId=` query param and returns a `devices` list so the page can render a picker. The JSON payload nests one object per child device - `inverter`/`solar`/`battery`/`grid` (the latter three `null` if that child hasn't been created yet) - each carrying every state that device has (`INVERTER_STATE_KEYS`/`SOLAR_STATE_KEYS`/`BATTERY_STATE_KEYS`/`GRID_STATE_KEYS`), not just the handful the four summary tiles show. The page renders those into the top summary tiles plus four "detail" cards (Solar strings table, Battery detail, Grid detail, Dispatch) below them. Dispatch also gets a one-line note in the header meta line (next to inverter temperature/work mode/system time) whenever `dispatchActive` is true, so an active dispatch is visible without scrolling to the detail card. All dynamic values are written into the page via `.textContent`/`createElement`/`replaceChildren`, never `.innerHTML`, so a device renamed to contain HTML/script content can't inject into the dashboard.

## Dependency management

`pymodbus` is declared in `requirements.txt` and installed automatically by Indigo on first launch — no vendored copy, no `sys.path` manipulation (same mechanism [Automate Pulse 2](https://github.com/coolcaper777/automate-pulse-2) uses for `aiopulse2`). An earlier version of this plugin manually vendored `pymodbus` into `Contents/Packages`, which required a `try/except NameError` fallback for `__file__` (Indigo `exec`s `plugin.py` rather than importing it, so `__file__` isn't defined at module scope) — that workaround is gone now that Indigo's own dependency installer manages the import path.

## Debug logging

`self.debug` / `self.indigo_log_handler` level is set from the `showDebugInfo` plugin preference (`PluginConfig.xml`) in `__init__` and re-applied live in `closedPrefsConfigUi` — no restart needed to toggle it. Debug-level logging covers every decoded register value per poll, keyed by state name.
